# Доставка заявок КэпСтрой

Обработчик запускает Telegram и MAX независимо. Успех формы (`302` на `/spasibo/`) — подтверждение **полной** заявки хотя бы одним API. Второй канал продолжает отправку независимо. Оба отказали или каналов нет — `500`, без ложной конверсии. CI-проверки и спам не отправляются.

## Настройки

| Environment контейнера | GitHub secret | Назначение |
| --- | --- | --- |
| `BOT_TOKEN` | `TELEGRAM_BOT_TOKEN` | Telegram-бот |
| `CHAT_ID` | `TELEGRAM_CHAT_ID` | Telegram-группа |
| `TELEGRAM_PROXY_URL` | `TELEGRAM_PROXY_URL` | Необязательный прокси, **только Telegram** |
| `MAX_BOT_TOKEN` | `MAX_BOT_TOKEN` | MAX-бот, токен через Authorization |
| `MAX_CHAT_ID` | `MAX_CHAT_ID` | Закрытая группа MAX, ID сохранять строкой |

Оба параметра канала пусты — канал выключен. Заполнить только один — ошибка конфигурации. Доступны Telegram-only, MAX-only, оба. Для запуска нужен хотя бы один полный набор. Без MAX-секретов текущая Telegram-схема сохраняется.

Токен не публиковать в чате, репозитории, аргументах команд или скриншотах. Использовать защищённый локальный environment / secret manager и GitHub production secrets. `.env` не коммитится; серверный `.env` создаётся с правами `600`.

## Подключение после модерации

1. Получить токен одобренного бота и поместить в локальный `MAX_BOT_TOKEN` безопасным способом. Не вставлять токен в историю команд.
2. Добавить бота в созданную закрытую **группу**, проверить права администратора. Не давать лишние права управления участниками.
3. Сразу после добавления выполнить из `form-handler`: `npm run max:discover`. Команда читает только `bot_added` и выводит ID групп, не сообщения пользователей. Выбрать ID именно группы заявок; при нескольких результатах ничего автоматически не сохраняется.
4. Задать локальный `MAX_CHAT_ID`, затем `npm run max:check`. Проверяются токен и членство бота без отправки сообщений.
5. По явному согласию выполнить `npm run max:send-test`. Это одно сообщение с пометкой **ТЕСТ**, без личных данных и без целей Метрики. Андрей подтверждает, что видит его.
6. Сохранить два MAX-секрета в production GitHub environment, интегрировать feature-ветку и выполнить деплой. API MAX требует актуального endpoint и отдельного TLS-agent; всё входит в образ.
7. После деплоя повторить read-only проверку `docker compose exec -T kepstroy-forms node check-delivery.js`, затем согласованную синтетическую проверку MAX. Реальную форму проверить отдельно и не считать тест лидом. CI-поля формы обходят мессенджеры — они **не** доказывают доставку.

`discover` — разовая настройка, не production long polling. Без marker API возвращает последнее обновление; события хранятся ограниченно. Если событие пропущено — повторно добавить бота в интерфейсе и сразу прочитать событие. Если уже есть Webhook-подписка, не отключать её автоматически: получить `chat_id` из её `bot_added`. Для постоянной обработки входящих событий нужен отдельный webhook-проект; текущая версия только отправляет заявки.

## Проверки и ограничения

`npm test` — транспорт, отказы/зависания, HTTP-формы, антиспам, TLS и setup. `npm run check:delivery` — только GET-проверки: Telegram `/getMe`, MAX `/me` и членство в выбранной группе. Проходит при доступности хотя бы одного настроенного канала; **это проверка связности, не подтверждение отправки сообщения**. `/health` остаётся локальной проверкой процесса.

HTTP deadline 8 секунд включает ответ и тело; MAX перенаправления запрещены. MAX-заявки разбиваются на части до 4000 Unicode-символов, без потери полей. Все MAX-запросы отправки в одном процессе сериализованы с интервалом не меньше 510 мс. Очередь ограничена 10 ожидающими заявками: ожидание максимум 8 секунд, затем задача удаляется без поздней отправки; активная доставка всех частей имеет общий бюджет 20 секунд. Переполнение очереди — отказ MAX, доступный Telegram всё равно может подтвердить заявку. Одновременный повтор по телефону блокируется до результата первой попытки; неуспешная попытка освобождает резервирование. Кнопка звонка в последней части; HTML пользователя отображается обычным текстом. Существующие Telegram-статусы сохраняются, MAX-статусы и синхронизация не реализованы.

Токены, телефоны, тексты и сырые API-ошибки не записываются в технические журналы доставки. Журнал содержит канал и `confirmed`/`failed`. Нет автоматического повторения POST после неопределённого ответа: оно может дублировать заявку. Нет долговечной очереди: перезапуск контейнера может прервать второй канал после успеха первого; при отказе обоих клиент видит ошибку и основной телефон. Для гарантированной доставки при полном отказе понадобится отдельный outbox/CRM, это не входит в первый этап.
