# Диагностика отправки форм

Внедрение 24.10.2026. Основные цели `form_submit` / `phone_click` прежние. Ошибки — диагностические события, их нельзя включать в приоритетные цели Директа.

| Событие | ID цели Метрики | Когда отправляется |
|---|---:|---|
| `solar_submit_error` | 674095266 | Отказ солнечной формы |
| `form_submit_error` | 674095267 | Отказ остальных форм |

Параметры: `reason` из закрытого списка, `http_status` (0 при отсутствии ответа), `request_id` только при корректном серверном UUID. В параметры не передаются поля формы, URL, исходная ошибка, номер телефона или текст заявки. Одна попытка вызывает одну соответствующую диагностическую цель; повторная осознанная попытка — отдельное событие.

Клиентские причины: `prepare_request` — не удалось подготовить данные/атрибуцию; `network` — fetch завершился исключением; `http_error` — неизвестный HTTP-отказ. Нативная проверка обязательных полей до submit остаётся браузерной валидацией, а не серверным отказом.

Серверные причины: `invalid_source`, `bot_check`, `invalid_form`, `invalid_payload`, `rejected_content`, `invalid_phone`, `rate_limit`, `payload_too_large`, `delivery_failed`, `internal_error`. Для отказов `/submit` ответ содержит `X-Request-ID` и `X-Form-Error`. Прокси, оборвавший запрос до приложения, может не вернуть эти заголовки.

Обработчик пишет JSON-строки в штатный stdout Docker:

```json
{"event":"form_submission","request_id":"случайный UUID","form":"solar","http_status":400,"reason":"invalid_phone","outcome":"rejected","duration_ms":3}
{"event":"form_delivery","request_id":"тот же UUID","channel":"max","status":"confirmed"}
```

Доставочные записи и итог HTTP относятся к одной попытке по UUID. При обрыве соединения `outcome: unknown`: канал может подтвердить доставку позже. `delivered` ставится после подтверждения хотя бы одного канала. `test_ignored` / `ignored` — существующий CI bypass, не реальный лид. Причина `delivery_failed` относится только к отказу доставки, а не к исключению до неё.

Журнал не содержит IP, телефона, тела формы, реферера, UTM, ClientID или токенов. Используется штатная ротация контейнера: три файла по 10 МБ. Ошибки фонового опроса Telegram — отдельные строки; они не доказывают отказ независимого MAX. После пересоздания контейнера старые локальные журналы могут стать недоступны; отдельное долговременное хранилище этой задачей не создавалось.

Проверки: локальные тесты `form-handler/test/submission-observability.test.js`, доставки, frontend runtime и передачи параметров аналитики. Внешние транспорты в тестах подменяются; реальные сообщения не отправляются. Проверка production отказом с пустым телефоном не подтверждает новую доставку, но позволяет связать HTTP-ответ и серверную запись. Историческую первопричину ошибки 12.10 новая инструментализация не восстанавливает.

Откат: вернуть предыдущий production-коммит приложения через штатный деплой; диагностические цели можно оставить без событий. Основные цели и доставка не зависят от новых целей. Новые мониторы, внешние платные сервисы и клиентские уведомления не добавлялись.
